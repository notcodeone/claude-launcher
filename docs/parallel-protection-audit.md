# Аудит защиты и общих компонентов Cowork

3 октября 2026. Состояние parallelism.7. Изучение кода и проверки на временных
файлах; авторизованные Cowork-задачи и наблюдение фактического трафика не выполнялись.

## Исправлено

Прежняя `EgressConfig.isPinned` проверяла только appliedId. Она могла подтвердить
конфигурацию с отсутствующей записью, чужим портом, прямым адресом или выключенной
блокировкой автообновлений. Теперь сверяются единственная запись лаунчера,
HTTP/127.0.0.1/порт без credentials, пути и query, disableAutoUpdates и режим 1p.
Kill Switch сравнивает порт с используемым затвором при первоначальном аудите и
появлении нового процесса. Процесс с неподходящей записью требует перезапуска;
редактирование файла не снимает это требование.

Чтение не различало отсутствующий и повреждённый файл: malformed JSON возвращал
null, после чего pin мог перезаписать конфигурацию как пустую. Теперь отсутствие
файла допускается, а нечитаемый/повреждённый/не-объектный JSON, симлинк или файл
больше 1 МиБ дают отказ. Чужой appliedId и некорректные entries сохраняются;
очистка удаляет лишь метаданные с применённой собственной записью.

Pin/read/unpin одного configDir выполняются последовательно, в том числе через
разные экземпляры EgressConfig. Это предотвращает пересечение операций разных
профилей в общей Windows-папке. Временная запись имеет уникальный каталог, затем
переименовывается. Очередь действует внутри одного процесса; изменение файлов
администратором или одновременно живущими процессами guard/launcher не является
транзакцией этой очереди. Несколько JSON-файлов также не заменяются одной транзакцией:
частично записанная конфигурация не проходит полную проверку isPinned.

## Границы изоляции

| Ресурс | Что делает лаунчер | Что ещё требуется проверить |
| --- | --- | --- |
| macOS config `<profile>-3p` | Подготавливает отдельную настройку профиля | Фактическое чтение каждым процессом, runtime-конфигурация VM |
| Windows `%LOCALAPPDATA%\Claude-3p` | Общая конфигурация, последовательные операции | Одна политика для всех; отдельные политики по аккаунтам не реализованы |
| Затвор EgressGate | Один общий порт и решение о сети; сеть блокируется глобально | Соединения без пути через затвор; процессная принадлежность потоков |
| Закрытие профиля | Закрывает выбранный Desktop-процесс, не останавливает общую службу Cowork | Что происходит с локальной задачей и соседней VM/интеграцией |
| CoworkVMService Windows | Общее правило firewall по имени службы | Enabled/Action/Direction/Service/профили/адреса действительного правила, реальный VM-трафик; текущий refresh проверяет только наличие имени |
| Аварийное завершение | Закрывает Desktop и поддержанные bundled Code-процессы; закрывает затвор | Уже запущенные VM, системные службы и процессы вне обнаруженного набора |
| MCP, браузер, подключённые папки | Не добавляет независимую изоляцию поверх Claude | Принадлежность вызовов/разрешений каждому аккаунту и отсутствие влияния на соседнюю задачу |
| Облачная задача Cowork | Лаунчер не управляет серверным исполнением | Прекращение local tool access при закрытии Desktop; выключение затвора не означает остановку облачной задачи |

Конфигурация файла и наличие firewall-правила не доказывают сетевую защиту.
Поддержка параллельного Cowork остаётся непроверенной.

Anthropic различает локальную работу agent loop на устройстве и выполнение кода
в VM; облачная сессия исполняется на сервере и обращается к локальным инструментам
через Desktop. Поэтому одного наблюдения Desktop PID недостаточно для полного
аудита: [официальная архитектура Cowork](https://support.claude.com/en/articles/14479288-claude-cowork-architecture-overview).

## Следующие испытания

1. Два тестовых аккаунта и две задачи с разными подключёнными временными папками.
   Для каждого аккаунта отдельно: локальная задача, код в VM, облачная задача
   с обращением к локальной папке; проверить принадлежность результата и разрешений.
2. Закрыть A: B сохраняет состояние, папку и связь; нет остановки общей службы.
   Отдельно проверить, продолжает ли VM/облачная задача A работать после закрытия.
3. Наблюдать дерево процессов и пути соединений до/после обрыва сети и остановки
   затвора; отдельно native loop, VM и MCP. Фиксировать лишь принадлежность и
   категории маршрута, без содержимого запросов/токенов/переписки.
4. Windows: проверить фактическую конфигурацию firewall и изменения администратором;
   наличие именованного правила недостаточно. Затем проверить общую службу при
   двух клиентах и отключении одного.
5. Передача guard → launcher и обратная передача при нескольких открытых профилях,
   смене порта и ошибке записи. Файловая сериализация внутри процесса не заменяет
   эту живую проверку.
