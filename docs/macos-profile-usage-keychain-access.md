# Однократный доступ к лимитам профилей на macOS

Решение зафиксировано 1 октября 2026 года. Это согласованное направление
исследования, а не реализованный механизм. Версия 1.2.0 читает локальную
историю лимитов без доступа к авторизации и Связке ключей.

## Что разрешает пользователь

При первом включении свежих лимитов пользователь вводит пароль macOS
в системном диалоге и выбирает «Всегда разрешать» для ClaudeLauncher.
Разрешение относится к элементу `Claude Safe Storage`, который нужен
для расшифровки существующей авторизации Claude Desktop.
Оно не даёт лаунчеру общий доступ ко всем паролям Связки ключей.

macOS умеет сохранять разрешение конкретному приложению и впоследствии
предоставлять доступ без повторного диалога.
[Документация Apple](https://support.apple.com/guide/mac-help/allow-apps-to-access-your-keychain-kychn002/mac).

## Почему разрешение не нужно для каждого нового профиля

OAuth-кэш и токены отдельные у каждого профиля. Лаунчер читает кэш выбранного
профиля после обычного входа в Claude и перечитывает его по мере обновления
авторизации. Дополнительный вход в Claude ради показа лимитов не нужен.

В Electron 44.4.3, найденном в установленном Claude Desktop, имена элемента
Keychain задаются по имени приложения: service — `<app_name> Safe Storage`,
account — `<app_name>`. Папка `--user-data-dir` и аккаунт Claude в этих именах
не участвуют. Поэтому профили одной установки Claude под одним пользователем
macOS используют общий элемент `Claude Safe Storage`.
[Исходник Electron: PostCreateMainMessageLoop](https://raw.githubusercontent.com/electron/electron/v44.4.3/shell/browser/electron_browser_main_parts.cc).

Создание очередного профиля само по себе не требует нового системного
разрешения. После обычного входа в нём лаунчер сможет расшифровать его кэш
через уже разрешённый общий ключ. Если Claude ещё не запускался и ключа
или авторизации нет, включение свежих лимитов следует отложить до их появления.

## Предлагаемая реализация

1. Читать ключ нативным кодом самого ClaudeLauncher. Не запускать `security`,
   Python или другой вспомогательный процесс при каждом обновлении.
2. Подписывать обновления одной постоянной подписывающей идентичностью,
   сохраняя идентификатор приложения и требование подписи, по которому
   Keychain узнаёт разрешённое приложение. Самоподписанный вариант рассмотрен
   в [документе о подписи](application-signing.md); он не обеспечивает публичное
   доверие Gatekeeper или нотариальное заверение Apple.
3. Хранить ключ и токен только в памяти, не записывать их в настройки,
   историю, логи или отчёты об ошибках. Пароль macOS обрабатывает системный диалог.
4. Выбирать авторизацию только из папки нужного профиля, проверять аккаунт
   и организацию. Использовать уже исследованный `/api/oauth/usage` для
   использованных процентов и серверного времени сброса `resets_at`.
5. После перезапуска снова читать ключ по сохранённому разрешению.
   Постоянным остаётся разрешение macOS, а не копия секрета у лаунчера.
6. Фоновые чтения выполнять с запретом интерактивного диалога. Если доступ
   недоступен, сохранять последний снимок и сообщать о невозможности обновления.
   Восстановление разрешения — только по явному действию пользователя.
7. Частоту запросов согласовать с поведением сервера: учитывать `Retry-After`,
   ограничивать повторные попытки и не обещать гарантированный интервал API.
   При истечении токена перечитывать кэш; не вмешиваться в обновление токенов Claude.

## Когда разрешение может понадобиться снова

Однократное разрешение — нормальный сценарий, а не обещание бессрочного доступа.
Повторное предоставление возможно при отзыве разрешения, пересоздании элемента,
смене подписывающей идентичности, переносе на другой Mac или другого пользователя.
Блокировка или недоступность связки также может временно остановить обновления.

При этом лаунчер не должен постоянно показывать запрос пароля. Получение лимитов
не требует открытого окна Claude Code. Использование нативного меню Claude
исключено по запросу пользователя.

## Что проверить перед включением

- Первое разрешение получает именно ClaudeLauncher, и оно относится только
  к необходимому элементу Keychain.
- Повторные обновления и перезапуск лаунчера не вызывают диалог.
- Новая сборка с той же подписывающей идентичностью сохраняет доступ.
- Новый профиль получает лимиты после обычного входа в Claude без второго входа
  и без нового разрешения Keychain.
- Данные нескольких профилей и организаций не смешиваются.
- Обновление токена, отказ API и ограничение частоты обрабатываются без цикла запросов.
- При заблокированной связке или отозванном доступе фоновые проверки не показывают диалог.
- Секреты отсутствуют в логах, настройках и файловых кэшах лаунчера.

Сохранение разрешения после перезапуска, обновления и создания нового профиля
ещё не проверено практически. Общая схема и вариант Windows описаны
в [исследовании источников лимитов](profile-usage-live-research.md).
