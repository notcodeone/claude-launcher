# Параллельные профили Claude: исследование и тестовая сборка

Дата: 3 октября 2026. Ветка `parallelism`, база `72bb1c6` (1.5.9).
Тестовая версия лаунчера: `1.5.10-parallelism.7+29`.
Flutter нормализует её в macOS Info.plist и интерфейсе до `1.5.10.7` (build 29).
Исследованный установленный Claude macOS: **2.19675.0**.

## Результат

Несколько процессов Claude с разными `--user-data-dir` одновременно работают
на проверенном Mac. Это подтверждено живым тестом двух новых профилей без
авторизации: оба сохранялись открытыми, закрытие A не закрыло B, существующие
процессы пользователя остались открыты. Тест направлял Chromium на неработающий
локальный прокси; это не аудит всех возможных сетевых путей Claude.

**Полноценная поддержка всех функций пока не доказана.** Запуск процессов не
проверяет независимость аккаунтов, OAuth, Code, Cowork и системных интеграций.
Windows изучен по коду проекта, без выполнения на Windows.

Повторный `open -n` с уже используемой папкой в этой версии Claude создал второй
главный процесс той же папки. Нельзя рассчитывать на автоматическую блокировку
«одна папка — один процесс». macOS-лаунчер показывает существующий экземпляр
по PID; синхронная блокировка операции дополнительно предотвращает два запуска
из быстрых нажатий. Это не защищает от независимого внешнего запуска Claude.

## Что реализовано в тестовой сборке

- Настройки → Эксперименты → **Параллельные профили — тест**. По умолчанию выключено,
  значение сохраняется между запусками. На главной странице виден статус теста.
- Запуск сохраняет остальные экземпляры, включая профили вне списка лаунчера.
  Показ существующего окна и закрытие выбранного профиля остаются адресными.
- Параллельный автозапуск использует отдельный набор: меню каждой карточки →
  «Открывать при запуске лаунчера». Запуски идут в порядке выбора, с проверкой
  каждого профиля. Уже открытый Claude отменяет весь набор; удалённые ID пропускаются.
  Ошибка или аварийное завершение останавливает оставшиеся запуски. Операции лаунчера
  резервируются на весь набор. Переключение в обычный режим прекращает оставшиеся
  запуски, уже начавшийся может завершиться. Старые настройки переносят прежний ID
  в набор; после этого выбор одиночного профиля и набора независим.
- На Windows показ существующего окна адресуется PID и повторно проверенной папке:
  предпочтительно видимое основное окно, иначе скрытое; восстановление из свёрнутого
  состояния. Окно выбирается по `Chrome_WidgetWin_1`, наличию заголовка и отсутствию
  владельца. Если окно не найдено или Windows отказала в фокусе — явная ошибка,
  без повторного запуска exe. Native-часть ещё не проверена на Windows.
- Проверка страны, подготовка уведомлений, значка и прокси выполняются перед
  каждым новым запуском. Ошибка подготовки не закрывает соседние профили.
- Запуск/закрытие/переход защищены от пересекающихся операций. Если выбранный
  процесс не обнаружен за 20 секунд, показывается ошибка, а не молчаливый успех.
- На macOS `claude://` отправляется Apple Event `GURL` по конкретному PID.
  Проверяются схема URL и bundle ID получателя; при ошибке нет fallback к общему
  системному обработчику. На Windows переходы при нескольких экземплярах пока
  заблокированы. Внешние ссылки из браузера лаунчер не перехватывает.
- Переход требует свежего успешного чтения процессов. Ошибка сканирования не
  допускает отправку по прежнему списку. Два процесса одного профиля дают отказ,
  а не произвольный выбор одного получателя.
- Уведомление содержит исходный `profileId` и `hostSessionId`. Закрытый профиль
  не подменяется оставшимся; старые уведомления без профиля открывают лаунчер.
- Новые и существующие сессии Code в параллельном режиме привязываются по файлу
  `claude-code-sessions/<account>/<org>/<hostSessionId>.json`: одновременно
  проверяются `sessionId` и `cliSessionId`. Ищем среди всех настроенных профилей,
  включая закрытые и MSIX-варианты пути. Копия в нескольких профилях, ошибка
  чтения, некорректный JSON или символическая ссылка не позволяют выбрать владельца.
  Никаких догадок по последнему открытому профилю. Уведомления без установленного
  владельца остаются общими. У опознанных в заголовке есть название профиля.
- Чтение метаданных ограничено по размеру и числу каталогов. События обрабатываются
  последовательно: завершение не обгоняет начало задачи при асинхронном чтении.
- Обновление Claude резервирует операции от закрытия до восстановления всех
  ранее открытых профилей. Набор фиксируется до установки; переключение режима
  во время неё не закрывает восстановленного соседа. Неизвестные экземпляры
  блокируют установку до закрытия; ошибка чтения списка процессов также блокирует.
- При отказе установки профили восстанавливаются только после проверки пригодности
  приложения (macOS — наличие версии и проверка codesign; Windows пока не объявляет
  такое восстановление допустимым). Ошибка одного запуска не пропускает следующие.
  Аварийное закрытие отменяет восстановление. На macOS резервная копия сохраняется
  при отказе отката и блокирует повторную замену до ручного восстановления.
- Kill Switch учитывает каждый работающий процесс при включении. Один профиль
  с прокси не скрывает необходимость перезапуска соседнего. Требование снимается,
  когда соответствующий процесс закрыт, а не только после закрытия всех Claude.
  Новые экземпляры после включения также проверяются по конфигурации; добавление
  прокси уже работающему процессу не снимает требование перезапуска. Это ещё не
  проверка фактических соединений и не доказательство защиты всех путей Cowork.
- Проверка настройки прокси требует полной записи и соответствия порту затвора.
  Внутри процесса операции общей конфигурации сериализованы, временные файлы
  уникальны. Повреждённый файл не перезаписывается как пустой; симлинки, не-объектный
  JSON и чужая применённая запись дают отказ. Это не подтверждает фактическую
  защиту VM: [отдельный аудит и матрица Cowork](parallel-protection-audit.md).
- Эта предварительная версия лаунчера не обновляется автоматически из стабильного
  канала. Следующую тестовую или стабильную сборку нужно установить вручную.

Выключение переключателя само по себе ничего не закрывает. **Следующий выбор
профиля в обычном режиме снова закрывает остальные**, включая действие показа.
Настройки, данные и bundle ID лаунчера общие со стабильной установкой: это замена
сборки, а не отдельная песочница. Не запускайте два лаунчера одновременно.

### Вход и маршрутизация ссылок

Адресная доставка ссылки из лаунчера и возврат из внешнего браузера — две разные
задачи. Даже успешный Apple Event по PID не исправит системную регистрацию URL.
Для полной поддержки нужен координатор входа, связывающий незавершённый flow с
профилем и доставляющий ответ именно ему. Нельзя рассылать callback всем процессам,
логировать коды авторизации или отключать проверки `state`/PKCE.

В обработчике URL установленного Claude 2.19675.0 Google-вход проверяет, что
ответ относится к входу, начатому этим экземпляром, и требует активного получателя
результата. Доставка в случайный процесс не завершит такой вход. Magic link и SSO
обрабатываются отдельными ветками с передачей в webview; MCP callback также имеет
отдельный маршрут. Поэтому координатор требует независимых испытаний Google,
email, SSO и MCP; успешный переход к Code-сессии не подтверждает эти сценарии.

Дополнительное исследование `.3`: в `_In` есть native `AuthRequest` /
ASWebAuthenticationSession. Он получает callback через результат `start()` и
передаёт его локальному `onCallback`, без выбора процесса системным URL-handler.
Но доступность, URL, remote flags и ошибки могут выбрать обычный браузер;
предусмотрен и timeout fallback. Google `hop_nonce` генерируется в процессе,
хранится в памяти до 30 минут и сверяется при ответе (есть зависимость от flags).
Поэтому отсутствие конфликтов в native-ветке не доказывает browser fallback.

Решение следующего этапа: сначала испытать native-ветку двумя аккаунтами и явно
проверить fallback. Для browser-ветки нужен наблюдаемый источник связи nonce с
PID; лаунчер сейчас не получает исходный запрос. Перехват только callback не
даст этой связи. Нельзя считать её установленной по выбранной карточке. Подробный
план: [parallel-auth-plan.md](parallel-auth-plan.md).

Перехват системного протокола потребует отдельного решения по установке,
восстановлению прежнего обработчика и обработке других видов ссылок Claude.
Простой выбор «последнего открытого профиля» недостаточен. Изменение bundle ID
копий Claude затрагивает подпись, обновления и системные разрешения; для первого
варианта оно не предлагается. Гарантировать вход без закрытия соседей до проверки
реального flow нельзя.

### Надёжная привязка Code

В сборке `.2` реализован вариант с профильным индексом Desktop. Структура пути
подтверждена кодом установленного Claude, наличие обоих строковых полей и совпадение
имени файла с `sessionId` — чтением схемы трёх локальных записей (их содержимое и
идентификаторы не сохранялись и не публиковались). Интеграционные тесты используют
полностью искусственные записи. Реальные авторизованные задачи не запускались.
В сборке `.3` неопознанные события временно сохраняются в памяти: до 256 событий
на две минуты. Поиск повторяется каждые две секунды, пока очередь не опустеет;
события применяются в исходном порядке без повторных уведомлений. Профиль должен
иметь процесс из снимка на момент события: перезапущенный сосед не наследует
задержанную задачу. Выключение интеграции, смена режима и выход очищают очередь.
В `.4` отдельный реестр восстанавливает до 256 недавних ссылок на сессии
(не старше часа) после перезапуска лаунчера. Кэш не доказывает принадлежность:
оба ID заново проверяются по профильным метаданным, получатель должен быть открыт.
Закрытый профиль, копия метаданных и несовпадение кэшированного владельца исключают
восстановление. До нового хука состояние «Неизвестно» с пояснением об отсутствии свежих событий: события во время
отсутствия лаунчера могли изменить задачу. Повторных уведомлений при восстановлении
нет. Реестр не хранит пути, названия/переписку, текст уведомлений или токены;
название и счётчики появятся после свежего события с путём transcript.

Возможный дополнительный источник — явный профильный маркер, наследуемый дочерним
Code и передаваемый разрешённым заголовком HTTP-хука. Сначала необходимо проверить,
что Desktop действительно сохраняет такое окружение при каждом способе запуска;
у `open`/MSIX/удалённых сессий это не доказано. Дополнительные варианты:
сопоставление host session ID с профильным индексом Desktop или процессным деревом.
Путь transcript полезен только после проверки, что он действительно находится
в уникальном хранилище профиля, а не в общей `~/.claude`.

Для полного режима нужен реестр `(profileId, hostSessionId, sessionId)` с
проверяемым источником привязки, восстановлением после перезапуска и состоянием
«владелец неизвестен». Текущий поиск по метаданным — проверяемая привязка для поддержанной схемы,
теперь дополнена восстановлением недавних ссылок после перезапуска. Актуальное
состояние требует свежего события. Для событий без установленного владельца нельзя
показывать состояние произвольного аккаунта.

### Windows: показ окна и транспорт URL

`WindowsWindowActivator` отделяет выбор/проверку HWND от Win32 вызовов. Fake-тесты
проверяют соседний PID, скрытое и свёрнутое окно, отсутствие основного окна,
смену владельца и отказ фокуса. `tool/window_activation_probe.dart` вызывает ту же
native-реализацию: `dart run tool/window_activation_probe.dart <PID>` на Windows.
Проверять на двух временных профилях, в том числе скрытом в трей и свёрнутом;
число процессов должно остаться прежним. Проба не запускает и не закрывает Claude.
Используется ShowWindowAsync, чтобы не ждать зависшего чужого UI-потока. Windows
может отказать SetForegroundWindow; обход ограничений через ввод не применяется.

Добавлена отдельная [проба и матрица проверки Windows](windows-parallel-verification.md):
точный PID/папка/время создания процесса, единственный receiver HWND, UTF-16
пакет, ограниченное ожидание и отсутствие повтора. Проба допускает только ссылки
Code и профили с явной папкой; в приложение ещё не подключена. Fake-тесты проверяют
адресность и отказы, native-транспорт требует живой Windows-проверки.

Исследование Chromium ProcessSingleton показывает доставку через скрытое окно
и WM_COPYDATA; это кандидат, а не внедрённый транспорт. Electron меняет формат
пакета дополнительными данными, поэтому копировать ванильный Chromium-пакет
без проверки версии нельзя. В установленном Claude macOS framework Electron
имеет версию 44.4.3; Windows-сборка и соответствие её протокола ещё не проверены.
До такой проверки `supportsTargetedLinks` на Windows остаётся false и переходы
при нескольких экземплярах блокируются. Авторизацию этот механизм также не решает.

### Cowork и границы изоляции

В текущей документации Anthropic описаны локальные и облачные режимы Cowork.
Они требуют разных проверок: отсутствие конфликта локальных VM не доказывает
корректность облачных задач с общими host-интеграциями, и наоборот. Поэтому прежнее
объяснение README «VM конфликтуют» рассматривается как причина консервативного
дизайна, а не установленный факт для всех нынешних версий.

Практические препятствия полной поддержки — внешняя маршрутизация авторизации,
источник принадлежности Code, общие службы/интеграции Cowork и проверяемая защита
каждого процесса. Они не решаются одним флагом запуска.

## Проверки и воспроизводимость

- `flutter analyze --no-pub`
- `flutter test --no-pub`
- `python3 tool/test_link_dispatch_macos.py` — два собственных AppKit-приёмника,
  проверка доставки только выбранному PID и отклонения не-Claude URL.
- `python3 tool/parallel_smoke_macos.py --links` — живые временные профили macOS,
  без авторизации; собственные процессы и каталоги убираются в `finally`.
- `flutter build macos --release`
- `bash tool/make_dmg.sh 1.5.10-parallelism.7`

Финальные результаты сборки и проверок — в `docs/parallelism-status.md`.

Перед выпуском полной поддержки нужна матрица macOS/Windows × основной/дополнительный
профиль × один/два/три экземпляра. Сценарии: одновременный вход; новая Code-сессия
в каждом; разрешение/вопрос/готовность; переходы из карточки, браузера и уведомления;
две Cowork-задачи; закрытие одного профиля; обновление обоих; перезапуск лаунчера;
обрыв VPN; новый внешний процесс; восстановление после сбоя. Критерий — соседний
профиль продолжает свою задачу, событие/ссылка не пересекает границу аккаунта,
защита не объявляется работающей без проверки реального пути трафика.
