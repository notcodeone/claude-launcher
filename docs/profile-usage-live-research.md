# Способы получения лимитов профиля

Исследование от 1 октября 2026 года. Это проект решения, а не включённая
реализация. Текущий лаунчер читает локальную историю лимитов.

## Требования и статус

Пользователю не подходят дополнительный вход и необходимость держать окно
Claude Code открытым. Полностью бесшумный новый источник без первоначального
доступа к существующей авторизации пока не подтверждён.

Нужны использованные проценты и серверное время сброса пятичасового и
недельного лимитов. Повторный вход и постоянно открытое окно Code исключены.
Далее методы разделены на подтверждённые источники, проекты интеграции и
отклонённые варианты. Проверка на Windows пока не проводилась.

| Способ | Второй вход | Окно Code | Проценты и сброс | Статус |
| --- | --- | --- | --- | --- |
| 1. OAuth-кэш Desktop → Usage API | Нет | Не нужно | Да | API проверен; новый доступ ещё не реализован |
| 2. Cookies того же Desktop-профиля → Web Usage API | Нет | Не нужно | Да | Запрос найден в Desktop; импорт cookies не проверен |
| 3. Нативное меню Claude в строке меню | Нет | Не нужно | Проценты и приблизительный сброс | Исключён по запросу пользователя |
| 4. Status line Code | Нет при существующем входе Code | Зависит от сессии | Да, после ответа модели | Не универсален для Desktop |
| 5. Управляющий канал SDK `get_usage` | Зависит от авторизации сессии | Возможен фоновый процесс | Да | Транспорт есть; подключения лаунчера к Desktop нет |
| 6. Локальная история | Нет | Не нужно | Только проценты | Уже используется |

## Способ 1. Сохранённая авторизация Desktop и OAuth Usage API

Практичный кандидат — исправить работу с уже сохранённой авторизацией:

1. Читать `Claude Safe Storage` нативным кодом самого лаунчера, а не отдельным
   процессом при каждом обновлении. Первоначальное разрешение macOS может
   потребоваться; это не повторный вход в Claude.
2. Держать ключ расшифровки только в памяти. Из OAuth-кэша выбранного профиля
   читать актуальный токен с `user:profile`, проверяя аккаунт и организацию.
   Не читать окружение работающего Code и не сохранять секреты лаунчером.
3. Использовать уже проверенный `/api/oauth/usage` для процентов и `resets_at`.
   Частота обновлений больше не зависит от записи истории раз в 4,5 минуты,
   но должна учитывать серверные ограничения и `Retry-After`.
4. Запретить интерактивную авторизацию при фоновых чтениях Keychain. Если
   доступ недоступен, не повторять диалог; оставить последний снимок. При
   необходимости восстановления доступа показывать его только по отдельному
   явному действию пользователя.
5. Обеспечить постоянную подписывающую идентичность приложения. Проверка
   `codesign -d -r-` текущей установленной и тестовой сборок показала разные
   требования `cdhash`. Это возможная причина утраты ранее разрешённого доступа
   после пересборки, но само поведение ACL в данном исследовании не проверялось.

Кэш в памяти теряется после выхода из лаунчера. На следующем запуске возможен
бесшумный доступ по сохранённому разрешению, но его нельзя гарантировать при
блокировке связки, отзыве доступа, смене подписи или пересоздании элемента.
Постоянная подпись не заменяет первоначальное разрешение пользователя.
Этот механизм не реализован и не проверен в текущем лаунчере.

### Одно разрешение на Mac для нескольких профилей

OAuth-кэш отдельный у каждого профиля: после обычного входа в Claude лаунчер
должен читать актуальный токен именно из выбранной папки. Кэш нужен и при
последующих обновлениях токена, а не только при создании профиля.

При этом ключ расшифровки не создаётся заново для каждого `--user-data-dir`.
В Electron 44.4.3 на macOS имена элемента Keychain устанавливаются из имени
приложения: service — `<app_name> Safe Storage`, account — `<app_name>`.
Папка профиля и аккаунт Claude в этих именах не участвуют. Для профилей одной
установки Claude под одним пользователем macOS это общий `Claude Safe Storage`.
[Electron 44.4.3, PostCreateMainMessageLoop](https://raw.githubusercontent.com/electron/electron/v44.4.3/shell/browser/electron_browser_main_parts.cc).

Предлагаемое поведение: при первом включении свежих лимитов нативный
ClaudeLauncher запрашивает доступ к этому элементу; пользователь вводит пароль
macOS и выбирает «Всегда разрешать». macOS сохраняет разрешение приложению,
что допускает последующие чтения без диалога. Создание нового профиля само
по себе не требует нового разрешения к тому же элементу или второго входа
в Claude. Если Claude ещё не запускался и элемент отсутствует, запрос нужно
отложить до появления сохранённой авторизации.
[Apple: Allow apps to access your keychain](https://support.apple.com/guide/mac-help/allow-apps-to-access-your-keychain-kychn002/mac).

Разрешение должно относиться к самому лаунчеру с постоянной подписывающей
идентичностью, а не к запускаемому им `security` или Python. После перезапуска
ключ снова читается нативно: постоянным остаётся разрешение, секрет хранится
только в памяти. При недоступной связке фоновые запросы не показывают диалог.
Смена подписи, отзыв разрешения или пересоздание элемента могут потребовать
повторного явного предоставления доступа. Практическая проверка сохранения
разрешения после перезапуска, обновления лаунчера и создания нового профиля
ещё не выполнена; это обязательные проверки перед включением механизма.

### Проработка для Windows

В обычной схеме DPAPI не требуется постоянная подпись лаунчера для доступа
к данным: важны тот же пользователь Windows, его доступ к файлам и обычно
тот же компьютер. Это отличается от ACL приложения в macOS Keychain.
Отдельные политики Windows и будущие изменения Claude могут ограничить доступ.
[Electron safeStorage](https://www.electronjs.org/docs/latest/api/safe-storage),
[Microsoft CryptUnprotectData](https://learn.microsoft.com/en-us/windows/win32/api/dpapi/nf-dpapi-cryptunprotectdata).

В установленном Claude Desktop 2.16120.0 для macOS найден Electron 44.4.3.
Его исходный код для Windows регистрирует ключи OSCrypt в `Local State`
и использует DPAPI key provider. Это подтверждает основу проекта, но не
подменяет проверку фактически установленного Windows Claude.
[Electron 44.4.3, BrowserProcessImpl](https://raw.githubusercontent.com/electron/electron/v44.4.3/shell/browser/browser_process_impl.cc).

Предлагаемый адаптер `WindowsProfileCredentialReader`:

1. Получить физические папки выбранного профиля через существующий
   `WindowsClaudeHost.readableDataDirs`. Стандартная MSIX-папка уже определяется
   как `%LOCALAPPDATA%\Packages\<family>\LocalCache\Roaming\Claude`.
   Пользовательский профиль может находиться в `%APPDATA%` или в виртуализированной
   папке того же пакета. Не привязываться к версии или выдуманному имени family.
2. Читать конфигурацию и `Local State` из одного физического хранилища.
   Не объединять токены из одной копии профиля с ключом другой копии.
   В установленном JavaScript подтверждены зашифрованные поля
   `oauth:tokenCache` и `oauth:tokenCacheV2`. Их структура версионируется;
   `lastKnownAccountUuid` — подсказка для выбора, а не окончательная проверка.
3. Для стандартного DPAPI/AES-GCM формата прочитать `os_crypt.encrypted_key`,
   декодировать Base64, проверить заголовок `DPAPI` и передать оставшийся blob
   в `CryptUnprotectData`. Эта схема подтверждается исходником key provider
   Chromium; неизвестный формат нельзя считать совместимым автоматически.
   [DPAPIKeyProvider](https://chromium.googlesource.com/chromium/src/+/refs/heads/main/components/os_crypt/async/browser/dpapi_key_provider.cc).
4. Вызвать DPAPI нативно, без PowerShell и дочерних консольных процессов:
   `pPromptStruct = NULL`, `CRYPTPROTECT_UI_FORBIDDEN`; обработать код ошибки
   и освободить `DATA_BLOB.pbData` через `LocalFree`. По документации Windows
   режим с запретом UI возвращает ошибку, если требуется взаимодействие.
   [Microsoft DPAPI](https://learn.microsoft.com/en-us/windows/win32/api/dpapi/nf-dpapi-cryptunprotectdata).
5. Расшифровать только поддерживаемый формат OAuth-кэша с проверкой тега
   целостности. Для AES-GCM подходит Windows CNG (`BCryptDecrypt`); размер nonce,
   расположение тега и дополнительные данные должны совпадать с соответствующей
   версией OSCrypt. Не передавать весь `v10`-blob напрямую в DPAPI: обычно DPAPI
   защищает ключ, а сам blob защищён AES-GCM.
   [Microsoft CNG](https://learn.microsoft.com/en-us/windows/win32/api/bcrypt/nf-bcrypt-bcryptdecrypt).
6. Выбрать только запись нужного аккаунта и организации с `user:profile`.
   Проверить её через `/api/oauth/profile`; не перебирать посторонние записи,
   общий CLI-вход или браузеры пользователя. Затем выполнить `/api/oauth/usage`.
7. Кэшировать ключ и авторизацию только в памяти. Перечитывать профиль при смене
   токена или ключа. На 401 перечитать кэш один раз; не обновлять refresh token
   параллельно с Desktop и не переписывать его OAuth-хранилище.

Политика сетевых обновлений общая для обеих ОС: один запрос на профиль в полёте,
обновление при открытии меню, затем ориентировочно каждые 30–60 секунд, пока оно
открыто. Это проект частоты, а не гарантия сервера. На 429 учитывать `Retry-After`,
на сетевых сбоях увеличивать задержку. Ключи, токены и заголовки не выводить в логи.
Для проверок личности и usage использовать заранее заданные HTTPS-хосты без
переадресации авторизации. Сброс хранить как серверную дату UTC и переводить
в локальное время при отображении, а не вычислять из процентов.

Что ещё проверить на Windows:

- Версию Electron, путь конфигурации и реальный формат ciphertext текущего Claude.
- MSIX и старую установку, стандартный и пользовательский профиль, переключение
  между двумя аккаунтами; подписанный и неподписанный лаунчер под обычным пользователем.
- Свернутое/закрытое окно Code, перезапуск лаунчера, смену токена и ключа,
  повреждённые данные, отказ DPAPI, 401 и 429. Ни один отказ не должен открыть
  консоль или запрос пароля.
- Сравнение пятичасового и недельного процентов и сбросов с экраном Usage
  выбранного профиля. Само чтение лимитов не должно запускать запрос к модели.

Подпись приложения рассмотрена отдельно в [application-signing.md](application-signing.md).

Основания:

- [Apple: Always Allow и индивидуальный доступ приложения](https://support.apple.com/guide/mac-help/kychn002/mac).
- [Apple: отказ без диалога, если требуется авторизация](https://developer.apple.com/documentation/security/ksecuseauthenticationuifail)
  — документация рекомендует современный `LAContext.interactionNotAllowed`.
- [Apple: подпись и designated requirement для Keychain](https://developer.apple.com/library/archive/technotes/tn2206/).
- [CodexBar: существующий OAuth, кэш и ограничения доступа](https://github.com/steipete/CodexBar/blob/main/docs/claude.md)
  — реализация другого приложения подтверждает подход к запросам usage, но
  использует источники авторизации CLI; это не готовая интеграция Desktop-профиля.

Ниже сохранены результаты проверки остальных кандидатов. Передачу токена
из работающего Code нельзя считать текущим решением: она требует сессии Code
и отдельного разрешения на новый источник секретов.

## Что подтверждено

В исходном JavaScript установленного Claude Desktop запись
`plan-usage-history.json` ограничена интервалом `270000` мс (4,5 минуты)
для одной организации. Повторное чтение файла не снимает эту задержку.
История содержит проценты, но не время сброса лимитов.

В предыдущей проверке запрос `GET https://api.anthropic.com/api/oauth/usage`
с авторизацией выбранного профиля вернул HTTP 200, проценты и `resets_at`.
Следовательно, для свежих данных не требуется ждать записи истории.
Этот endpoint не является документированным публичным API; его доступность,
формат ответа и ограничения частоты могут измениться.

Функция `aY` в установленном Claude Desktop передаёт запускаемому Claude Code
переменную `CLAUDE_CODE_OAUTH_TOKEN`. Функция `bEr` формирует переменные
`CLAUDE_CODE_ACCOUNT_UUID` и `CLAUDE_CODE_ORGANIZATION_UUID`.
Это кандидат на источник авторизации без расшифровки сохранённого OAuth-кэша.
Реальное наличие токена в работающей сессии ещё не проверено.

Файлы `host-creds-*.json` относятся к брокеру сторонних провайдеров.
В проверенной папке активного профиля их нет; считать их универсальным
источником для обычной подписки Claude нельзя.

## Предлагаемое поведение

Историческая гипотеза передачи авторизации от Code. Не является выбранным
вариантом и не удовлетворяет требованию работы без сессии Code. Пункт про
возраст снимка ниже относится к старому предложению: по текущему запросу
пользователя дата получения и предупреждение об устаревании в меню удалены.

1. Получать действующий OAuth-токен только от Claude Code, запущенного
   приложением Claude для выбранного профиля. CLI и Desktop запускаются
   исключительно через ClaudeLauncher.
2. Проверять привязку к аккаунту и организации текущего профиля. Не использовать
   общий вход CLI и не перебирать авторизации других профилей.
3. Хранить токен только в памяти; не записывать его на диск и не выводить в логи.
   При закрытии или смене профиля удалять его из памяти.
4. Запрашивать лимиты при открытии подменю и затем каждые 30 секунд, пока оно
   открыто. Разрешать ручное обновление. При HTTP 429 учитывать `Retry-After`;
   не обещать неограниченную частоту запросов.
5. Отправлять авторизацию только на заранее заданные HTTPS endpoint Anthropic;
   отключить перенаправления и сохранить проверку TLS.
6. Отображать время обновления, остаток и время сброса. Если токен отсутствует
   или истёк, показывать локальный снимок с явным указанием его возраста.

Возможен официальный транспорт через существующие локальные HTTP-хуки:
они поддерживают интерполяцию явно разрешённых переменных окружения в
заголовки. Для этого потребуется отдельно проверить, что токен доступен
HTTP-хуку именно в Desktop-сессии; документация не гарантирует этот факт.
Не следует обходить запрет чтения окружения процесса передачей того же
секрета через хук без разрешения пользователя.

## Что требуется для проверки

Автоматическая проверка отклонила чтение окружения дочернего Claude Code:
прежнее разрешение пользователя распространялось на сохранённую авторизацию
профиля, а не на секреты работающего процесса. Токен из окружения не прочитан.
Для проверки этого нового источника требуется отдельное разрешение.

При отсутствии сессии Code получить такой токен этим путём невозможно.
После перезапуска лаунчера или истечения токена может потребоваться новая
передача авторизации от Code. Эти ограничения нужно проверить перед тем,
как объявлять решение готовым.

Документация Anthropic:

- [HTTP-хуки и allowedEnvVars](https://code.claude.com/docs/en/hooks#http-hook-fields)
- [Лимиты в status line](https://code.claude.com/docs/en/statusline#rate-limit-usage)
  — дополнительный путь без передачи токена, но данные появляются после
  ответа API и документированы для общего пятичасового и недельного лимита.

## Проверка существующего перехвата событий

В ClaudeLauncher события поступают через HTTP-хуки `UserPromptSubmit`,
`PostToolUse`, `Notification`, `Stop` и `SessionEnd`. Это не весь поток SDK.
В установленном Claude Code 2.1.284 функция формирования общих полей хуков
и функция формирования `Stop` не добавляют проценты лимитов.
Добавление обработчика поля `rate_limits`, которого отправитель не передаёт,
не обеспечит свежие данные.

В бинарном коде той же установленной версии найден экспериментальный
SDK-запрос `get_usage` с опцией `skip_behaviors: true`. Он возвращает
структурированные данные `/usage`, включая лимиты подписки, и может быть
основой решения без получения OAuth-токена лаунчером. Однако существующий
HTTP-приёмник не подключён к управляющему каналу SDK; сессией внутри Desktop
управляет сам Desktop. Подключение к этому каналу ещё не реализовано и не
проверено. Через ответ существующего HTTP-хука такой запрос не отправляется.

Отдельные сообщения SDK `rate_limit_event` тоже не являются HTTP-хуками.
Они приходят при изменении состояния ограничения, а `utilization` может
отсутствовать. Поэтому нельзя считать этот поток гарантированным источником
полного остатка всех лимитов.

- [Поля Stop-хука](https://code.claude.com/docs/en/hooks#stop-input)
- [Типы событий SDK](https://github.com/anthropics/claude-agent-sdk-python/blob/main/src/claude_agent_sdk/types.py)

## Уточнение: окно Claude Code не должно требоваться

Чтение через macOS Accessibility проверено на открытом окне Usage: проценты,
пятичасовой сброс в относительном формате и недельный сброс доступны в дереве
интерфейса. Пользователь отклонил этот вариант, поскольку он требует открытого
окна. Чтение через Accessibility в лаунчер не добавлено.

Проверен также `CLAUDE_CODE_PROCESS_WRAPPER`. Установленный Desktop удаляет
этот параметр из обычного окружения. Корпоративный режим обёртки работает
с управляемыми настройками и не передаёт обёртке авторизацию самого Desktop.
Поэтому он не решает задачу простого получения лимитов текущего профиля.

## Локальный отладочный канал Electron

Проверено не только основное приложение, но и предварительный код запуска
`/.vite/build/index.pre.js` из установленного `app.asar`. Функция `lZ`
обнаруживает `remote-debugging-port` и `remote-debugging-pipe`; без внутреннего
подписанного разрешения Claude выводит отказ в запуске и выполняет
`process.exit(1)`. Поэтому обычный CDP-запрос через уже авторизованный Desktop
не является доступным решением. Claude с такими параметрами не запускался,
бинарник и проверка подписанного разрешения не изменялись.

Установленный Electron Framework имеет fuse `EnableNodeCliInspectArguments`
в состоянии `0`; доступ через Node inspector также не является штатной
альтернативой. Значения fuse прочитаны из бинарника, без запуска Claude.

## Отдельная веб-сессия лаунчера

WebKit позволяет изолировать постоянные cookies по профилям. Это даёт основу
для фонового web API без чтения Keychain Claude, но требует отдельного входа.
Пользователь отклонил два входа. Веб-сессия не создавалась и не добавлялась.

## Способ 2. Cookies уже авторизованного Desktop-профиля

Это отличается от отклонённой отдельной веб-сессии: используется существующий
вход самого Desktop, без создания новой сессии в лаунчере.

В установленном Claude найден запрос
`GET <origin>/api/organizations/<org>/usage`, выполняемый Electron `net.fetch`.
Схема ответа содержит `limits[].percent`, `kind`, `group`, `resets_at` и `scope`.
План: читать только session cookie (`sessionKey`) выбранного Desktop-профиля,
проверять его аккаунт/организацию и вызывать этот же web endpoint.
Cookies чужих браузеров не нужны. Аналогичный web API используется в
[CodexBar](https://github.com/steipete/CodexBar/blob/main/docs/claude.md).

macOS: импорт Chromium cookies потребует системного ключа расшифровки и обычно
того же первоначального разрешения Safe Storage, что способ 1. Windows:
вероятен DPAPI/AES-GCM адаптер. Нужно проверить папку/partition cookie store,
SQLite-схему и версию шифрования. При чтении работающей SQLite-базы использовать
корректный снимок с учётом WAL; исходную базу не изменять.

Преимущество: может работать, когда Desktop ещё не сохранил подходящий
OAuth-токен или его scope не даёт читать usage. Ограничения: не снимает
первоначальный доступ к расшифровке на Mac; web endpoint может выдавать
Cloudflare-проверку, а сессия — истечь. Получение cookie из этого профиля и
сам запрос лаунчером ещё не проверены. Это отдельный кандидат, а не готовый fallback.

## Способ 3. Нативное меню Claude в строке меню macOS — исключён

Пользователь исключил использование нативного меню Claude. Следующие сведения
сохранены как результат исследования; дальнейшая реализация не планируется.

В установленном коде найдено `trayUsage.popUp`. Desktop передаёт нативному
модулю строки из `Ani()`/`Dni()`: название лимита, долю использования и
описание сброса. Действие `refresh` вызывает `T1({interaction: true})`.
Открывать страницу Code или Usage для этого по коду не требуется — нужен
работающий Desktop и его значок в строке меню.

Можно исследовать чтение этих строк через Accessibility, без получения
токенов лаунчером. Оно отличается от отклонённого чтения открытого окна Usage.
Но доступны ли строки при закрытом меню, потребует проверки; открытие меню
может быть заметно и мешать пользователю. На Mac самому лаунчеру понадобился
бы доступ Accessibility. Новый доступ не запрашивался.

Точность ограничена: `Mni()` округляет сброс до минут, часов или дней, поэтому
по этому тексту нельзя восстановить точную серверную дату. Наличие меню зависит
от feature flag. Запасное меню `wni()` показывает только максимальный процент,
без отдельных окон и сбросов. Это не подтверждённый универсальный вариант для
Windows. Практическое чтение меню в этой проверке не выполнено.

## Способ 4. Status line работающей сессии Code

Официальный JSON status line содержит `rate_limits.five_hour` и `seven_day`
с полями `used_percentage` и `resets_at` (Unix seconds). Это позволяет получать
данные без передачи авторизации лаунчеру. Поля появляются после первого ответа
API и могут отсутствовать независимо друг от друга.
[Документация Anthropic](https://code.claude.com/docs/en/statusline#rate-limit-usage).

При существующем терминальном входе можно сохранять только эти поля callback-ом.
Однако текущая интеграция лаунчера получает HTTP-хуки Desktop-сессий; status line
в их headless/SDK-режиме не подтверждён и ранее не был найден как рабочий источник.
Метод зависит от сессии и активности Code, не обновляет произвольный профиль
по требованию и не покрывает всё время работы Desktop. Любой тестовый Code
можно запускать только через ClaudeLauncher.

## Способ 5. Управляющий канал SDK

Экспериментальный `get_usage` описан выше: он потенциально подходит для
фонового процесса без окна и возвращает структурированные лимиты. Для чужой
Desktop-сессии у лаунчера сейчас нет управляющего соединения. Собственный
SDK-процесс всё равно должен получить авторизацию выбранного профиля, поэтому
его нельзя объявлять решением проблемы доступа к входу. Инъекция в stdin/stdout
существующего процесса не реализована. API экспериментален.

## Способ 6. Локальная история и неподходящие источники

История уже используется и остаётся доступной без секретов. Интервал записи
4,5 минуты ограничивает её свежесть, а сбросы отсутствуют. Включение более
частого перечитывания не добавит недостающих данных.

Официальные Usage/Cost и Rate Limits API тоже проверены как кандидаты.
Они относятся к API-организации, её потреблению и ограничениям; требуют
соответствующих административных учётных данных. Это не универсальный источник
пятичасового/недельного остатка подписки личного Desktop-профиля.
[Usage and Cost](https://platform.claude.com/docs/en/manage-claude/usage-cost-api),
[Rate Limits API](https://platform.claude.com/docs/en/manage-claude/rate-limits-api).

Проценты подписки нельзя восстановить точным расчётом по локальным токенам
или времени последнего сообщения. Значение отсутствующего сброса остаётся
неизвестным; подставлять время, вычисленное эвристикой, не следует.

Рекомендуемый порядок следующей проверки: способ 1 на Windows (DPAPI),
затем способ 1 на Mac с постоянной идентичностью подписи; способ 2 — отдельная
проверка при отсутствии подходящего OAuth-кэша. Способ 3 исключён по запросу
пользователя. Ни один новый источник в приложение пока не подключён.
