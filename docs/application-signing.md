# Постоянная подпись без аккаунтов разработчика

Исследование от 1 октября 2026 года. Сертификаты не создавались, системное
доверие не менялось, рабочие сборки и CI не переподписывались.

## Что можно обеспечить

На обеих ОС можно создать собственный сертификат Code Signing и использовать
одну и ту же пару сертификат/закрытый ключ для последующих сборок. Для этого
не нужны аккаунты Apple Developer или Microsoft Partner Center. Подпись каждого
нового файла будет другой, но идентичность подписанта может оставаться постоянной.
Это не эквивалент публичному доверию ОС к издателю.

| Задача | macOS | Windows |
| --- | --- | --- |
| Собственная постоянная идентичность | Самоподписанный Code Signing сертификат и устойчивый designated requirement | Самоподписанный Code Signing сертификат и Authenticode |
| Аккаунт разработчика для этого | Не нужен | Не нужен |
| Польза для получения лимитов | Помогает сохранять разрешение Keychain между сборками | Обычный DPAPI не привязан к подписи вызывающей программы |
| Автоматическое доверие на чужом компьютере | Не даёт | Не даёт |
| Предупреждения при скачивании | Gatekeeper остаётся отдельной задачей | SmartScreen остаётся отдельной задачей |

## macOS

Apple документирует создание самоподписанной Code Signing identity через
Certificate Assistant или OpenSSL. Для Keychain важен designated requirement
(DR), по которому система узнаёт приложение при обновлении; он может опираться
на собственный сертификат. Это применимо к внутренним сборкам.
[Apple Code Signing Tasks](https://developer.apple.com/library/archive/documentation/Security/Conceptual/CodeSigningGuide/Procedures/Procedures.html),
[TN2206](https://developer.apple.com/library/archive/technotes/tn2206/).

### Что обнаружено в проекте

- `codesign -d -r-` установленной и тестовой сборок показывает DR через разные
  `cdhash`, а не через постоянную сертификатную идентичность.
- `tool/make_dmg.sh` явно выполняет `codesign --force --deep --sign -`.
  Даже если подписать приложение ранее своим сертификатом, этот шаг снова
  заменит подпись на ad-hoc.
- `.github/workflows/build.yml` собирает приложение Flutter и затем вызывает
  этот скрипт. Постоянная signing identity в workflow не настроена.

### Проект изменений

1. Один раз создать Code Signing сертификат с закрытым ключом, выбрать срок
   действия и сохранить резервную копию identity вне репозитория. Не генерировать
   новую identity при каждом build. Нужен закрытый ключ, одного `.cer` недостаточно.
2. Сохранять bundle identifier и DR, привязанный к подписывающему сертификату.
   Зафиксировать ожидаемое требование и проверять его у локальной и CI-сборок.
   Имя сертификата само по себе не является стабильным идентификатором.
3. Подписывать вложенный исполняемый код и frameworks, затем внешний `.app`
   с необходимыми Flutter entitlements. Последующая упаковка должна сохранять
   эту подпись. `--deep` не использовать как замену продуманному подписанию
   всех вложенных компонентов.
4. Передать identity в сборку и упаковку; убрать безусловную ad-hoc переподпись
   из `make_dmg.sh`. На CI импортировать `.p12` из защищённого секрета в временную
   связку только для подписания, потом очищать временную связку.
5. Проверить подпись и DR двух разных сборок. На первом запуске явно разрешить
   только лаунчеру доступ к нужному элементу Keychain. Убедиться, что после
   обновления разрешение сохраняется. Фоновое чтение всё равно должно запрещать UI.

Постоянная подпись уменьшает проблему идентификации сборок, но не гарантирует
доступ при блокировке Keychain, изменении ACL, отзыве разрешения или пересоздании
элемента. Создание сертификата и первоначальное разрешение — отдельные операции,
а не второй вход в Claude.

Самоподписанный сертификат не даёт Developer ID, Team ID от Apple или
нотариализацию. Для штатной публичной дистрибуции через Gatekeeper Apple
описывает Developer ID и Apple Developer Program; собственный сертификат не
снимает это требование. [Apple Developer ID](https://developer.apple.com/developer-id/).

## Windows

Windows предоставляет `New-SelfSignedCertificate` для собственной Code Signing
identity и `SignTool` для подписания файлов. Это можно сделать без Microsoft
developer account. Одну identity нужно сохранять и использовать при обновлениях.
[Microsoft PKI](https://learn.microsoft.com/en-us/powershell/module/pki/new-selfsignedcertificate),
[Microsoft SignTool](https://learn.microsoft.com/en-us/windows/win32/seccrypto/signtool).

### Что обнаружено в проекте

- Сейчас лаунчер выпускается как EXE с Inno Setup и portable ZIP.
  Claude установлен MSIX-пакетом, но это не означает, что сам лаунчер — MSIX.
- В `.github/workflows/build.yml` нет Authenticode-подписания EXE или установщика.
- Постоянный `AppId` в `windows/installer/claude_launcher.iss` обеспечивает
  идентичность установки; он не является цифровой подписью.

### Проект изменений

1. Один раз создать Code Signing сертификат в хранилище подписывающего
   пользователя; сохранить identity/PFX вне репозитория и резервировать ключ.
2. Подписывать `claude_launcher.exe` после сборки и до копирования в portable ZIP
   и Inno Setup. Не изменять исполняемый файл после подписания.
3. Подписывать конечный установщик и при необходимости его деинсталлятор через
   настройки Inno Setup SignTool. В CI использовать защищённый секрет PFX.
4. Проверять Authenticode у конечных артефактов и одинакового подписанта у двух
   версий. При использовании доверенного timestamp учитывать правила выбранного
   сервиса; он не превращает самоподписанный сертификат в публично доверенный.
5. На собственных/управляемых компьютерах можно отдельно настроить доверие
   к открытому сертификату. Не встраивать автоматическое расширение системного
   доверия в установщик как условие чтения лимитов.

Самоподпись сама по себе не даёт положительную репутацию SmartScreen. Даже
подпись сертификатом публичного CA не гарантирует отсутствие предупреждения
у нового файла. Для публичной Windows-дистрибуции есть CA-сертификаты и
Artifact Signing; это отдельные платные варианты с проверкой издателя, не
тождественные Microsoft Store developer account.
[Microsoft SmartScreen reputation](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/smartscreen-reputation).

Если когда-либо перейти на MSIX, понадобится подпись пакета и доверие к
сертификату на целевом компьютере. У самоподписанного MSIX сертификат сначала
развёртывается в предусмотренное хранилище доверия; текущему EXE-установщику
это правило не следует приписывать.
[Microsoft MSIX signing](https://learn.microsoft.com/en-us/windows/msix/package/sign-msix-package-guide).

## Проверка перед внедрением

Для Mac проверить сохранение доступа Keychain после реального обновления,
включая универсальную сборку и приложение из DMG. Для Windows отдельно
проверить подпись EXE/установщика и чтение DPAPI под обычным пользователем:
эти две проверки решают разные задачи. Самоподписанные сертификаты подходят
для постоянной идентичности собственных сборок; публичное доверие не обещается.
